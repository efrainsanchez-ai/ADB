Capacity Planning Using Current Usage

Capacity planning estimates future CPU, storage, and workload requirements from observed usage. Use database views for local detail, OCI Monitoring for service-level metrics, OCI alarms for thresholds, and Operations Insights for fleet-level trend and forecast analysis.

Guide index Previous: 23ai and 26ai New Features Next: Autonomous AI Database MCP Server

What it is

Capacity planning is the process of translating current usage into future resource requirements. For Autonomous Database, the useful inputs are CPU utilization, average active sessions, queued statements, execution rate, transaction rate, physical I/O, storage used, storage growth, and application concurrency.

Capacity Planning Signal Chain
Database Detail SQL snapshots, top SQL, segments, AAS, and p95 CPU.
OCI Metrics CpuUtilization, StorageUsed, queued statements, I/O, and transactions.
Forecast Operations Insights, growth rate, trend windows, and fleet ranking.
Decide Scale, tune SQL, compress, partition, or adjust auto scaling.

Metric area What to measure Planning use
CPU Average, peak, and p95 CPU utilization. Estimate base ECPU requirements and headroom.
Concurrency Average active sessions, running statements, queued statements, sessions. Identify saturation, queuing, or service-level pressure.
Storage Storage used, reserved storage, growth per month, largest segments. Estimate storage allocation and compression opportunities.
Workload Executions, user calls, commits, top SQL, I/O volume. Separate scaling needs from SQL tuning opportunities.

OCI services add the cloud control-plane view that SQL alone cannot provide. Use them to trend service metrics over time, compare multiple databases, create threshold alarms, and plan compute or storage changes from the same resource model used by the OCI Console and APIs.

Why it matters

Sizing from a single peak or a rough user count is unreliable. Current usage trends show whether the database needs more base capacity, auto scaling, SQL tuning, compression, partitioning, or connection-service changes. The best capacity plan uses both database-level detail and OCI service metrics because the database view explains workload behavior while the OCI view explains provisioned capacity, cloud service utilization, and fleet trends.

Check if enabled

Capacity planning is not a feature switch. Check whether you already collect snapshots, then review current storage and workload pressure. 

-- Check whether a local capacity snapshot table exists.
SELECT table_name
FROM   user_tables
WHERE  table_name = 'CAPACITY_USAGE_SNAPSHOT';
-- Check whether a scheduled snapshot job exists.
SELECT job_name,
       enabled,
       state,
       repeat_interval,
       last_start_date,
       next_run_date
FROM   user_scheduler_jobs
WHERE  job_name = 'CAPACITY_USAGE_SNAPSHOT_JOB';

Review current database storage, top segments, and top SQL. These checks help distinguish resource growth from individual SQL problems. 

-- Current storage usage by schema.
SELECT owner,
       ROUND(SUM(bytes) / POWER(1024, 3), 2) AS used_gb
FROM   dba_segments
GROUP  BY owner
ORDER  BY used_gb DESC
FETCH FIRST 20 ROWS ONLY;
-- Largest segments.
SELECT owner,
       segment_name,
       segment_type,
       ROUND(bytes / POWER(1024, 3), 2) AS size_gb
FROM   dba_segments
ORDER  BY bytes DESC
FETCH FIRST 30 ROWS ONLY;
-- Current workload indicators.
SELECT metric_name, value, metric_unit
FROM   v$sysmetric
WHERE  metric_name IN (
  'Host CPU Utilization (%)',
  'Average Active Sessions',
  'Executions Per Sec',
  'User Calls Per Sec'
)
ORDER  BY metric_name;
-- Top SQL by total elapsed time.
SELECT sql_id,
       executions,
       ROUND(elapsed_time / 1e6, 1) AS total_elapsed_sec,
       ROUND(elapsed_time / NULLIF(executions, 0) / 1e6, 3) AS avg_elapsed_sec,
       ROUND(cpu_time / 1e6, 1) AS total_cpu_sec,
       buffer_gets,
       disk_reads,
       SUBSTR(sql_text, 1, 100) AS sql_preview
FROM   v$sqlarea
WHERE  executions > 0
ORDER  BY elapsed_time DESC
FETCH FIRST 20 ROWS ONLY;

How to enable

For local trend analysis, create a lightweight snapshot table and schedule periodic captures. Hourly snapshots are usually more useful than one daily sample because they show workload shape across business hours and batch windows. 

-- Create a local capacity snapshot table.
CREATE TABLE capacity_usage_snapshot (
  sample_time          TIMESTAMP WITH TIME ZONE DEFAULT SYSTIMESTAMP NOT NULL,
  cpu_util_pct         NUMBER,
  avg_active_sessions  NUMBER,
  executions_per_sec   NUMBER,
  user_calls_per_sec   NUMBER,
  segment_used_gb      NUMBER
);
-- Insert one snapshot manually.
INSERT INTO capacity_usage_snapshot (
  cpu_util_pct,
  avg_active_sessions,
  executions_per_sec,
  user_calls_per_sec,
  segment_used_gb
)
WITH m AS (
  SELECT metric_name, MAX(value) AS value
  FROM   v$sysmetric
  WHERE  metric_name IN (
    'Host CPU Utilization (%)',
    'Average Active Sessions',
    'Executions Per Sec',
    'User Calls Per Sec'
  )
  GROUP  BY metric_name
),
s AS (
  SELECT SUM(bytes) / POWER(1024, 3) AS segment_used_gb
  FROM   dba_segments
)
SELECT MAX(CASE WHEN metric_name = 'Host CPU Utilization (%)' THEN value END),
       MAX(CASE WHEN metric_name = 'Average Active Sessions' THEN value END),
       MAX(CASE WHEN metric_name = 'Executions Per Sec' THEN value END),
       MAX(CASE WHEN metric_name = 'User Calls Per Sec' THEN value END),
       MAX(s.segment_used_gb)
FROM   m
CROSS  JOIN s;
-- Commit the manual capacity snapshot.
COMMIT;

Schedule the same capture hourly. In production, choose a retention policy and purge old local snapshots if you keep this table long term. 

BEGIN
  DBMS_SCHEDULER.CREATE_JOB(
    job_name        => 'CAPACITY_USAGE_SNAPSHOT_JOB',
    job_type        => 'PLSQL_BLOCK',
    job_action      => q'[
      BEGIN
        INSERT INTO capacity_usage_snapshot (
          cpu_util_pct,
          avg_active_sessions,
          executions_per_sec,
          user_calls_per_sec,
          segment_used_gb
        )
        WITH m AS (
          SELECT metric_name, MAX(value) AS value
          FROM   v$sysmetric
          WHERE  metric_name IN (
            'Host CPU Utilization (%)',
            'Average Active Sessions',
            'Executions Per Sec',
            'User Calls Per Sec'
          )
          GROUP BY metric_name
        ),
        s AS (
          SELECT SUM(bytes) / POWER(1024, 3) AS segment_used_gb
          FROM   dba_segments
        )
        SELECT MAX(CASE WHEN metric_name = 'Host CPU Utilization (%)' THEN value END),
               MAX(CASE WHEN metric_name = 'Average Active Sessions' THEN value END),
               MAX(CASE WHEN metric_name = 'Executions Per Sec' THEN value END),
               MAX(CASE WHEN metric_name = 'User Calls Per Sec' THEN value END),
               MAX(s.segment_used_gb)
        FROM   m
        CROSS JOIN s;

        COMMIT;
      END;
    ]',
    start_date      => SYSTIMESTAMP,
    repeat_interval => 'FREQ=HOURLY;INTERVAL=1',
    enabled         => TRUE,
    auto_drop       => FALSE,
    comments        => 'Hourly local capacity usage snapshot'
  );
END;

Enable the OCI services that support the planning workflow. Monitoring metrics are available from the service namespace; alarms, Operations Insights, and Database Management dashboards require the appropriate OCI permissions and service configuration.

Planning task OCI service action Practical guidance
Build metric charts Create Metrics Explorer queries against oci_autonomous_database. Track 30, 60, and 90-day trends for CPU, storage, sessions, queued statements, and I/O.
Create alerts Create Monitoring alarms and route them through Notifications. Use sustained thresholds rather than short spikes, for example 30 to 60 minutes of high utilization.
Forecast fleet needs Enable Operations Insights and use Capacity Planning. Compare top consumers, growth rates, and forecasted CPU or storage pressure across compartments.
Review database details Use Database Management after Operations Insights is enabled. Use the Capacity Planning dashboard for recent data and drill down to Operations Insights for deeper analysis.
Apply capacity changes Use Autonomous Database resource allocation in the OCI Console or API. Adjust base ECPUs, storage, compute auto scaling, or storage auto scaling after validating demand and cost impact.
For Autonomous Database Serverless, compute auto scaling is enabled by default and storage auto scaling is disabled by default. Compute auto scaling can use up to three times the base ECPU or OCPU count, and storage auto scaling can expand up to three times reserved base storage, subject to documented limits and billing behavior.

Test example

Use snapshots to estimate growth and calculate p95 usage. For a more complete view, compare these local results with OCI Monitoring metrics such as CpuUtilization, StorageUsed, StorageUtilization, StorageMax, TransactionCount, UserCalls, PhysicalReadTotalBytes, and PhysicalWriteTotalBytes. 

-- Estimate monthly storage growth from local snapshots.
SELECT MIN(sample_time) AS first_sample,
       MAX(sample_time) AS last_sample,
       ROUND(MIN(segment_used_gb), 2) AS first_used_gb,
       ROUND(MAX(segment_used_gb), 2) AS last_used_gb,
       ROUND(
         (MAX(segment_used_gb) - MIN(segment_used_gb)) /
         NULLIF(MAX(CAST(sample_time AS DATE)) - MIN(CAST(sample_time AS DATE)), 0) * 30,
         2
       ) AS estimated_growth_gb_per_month
FROM   capacity_usage_snapshot;
-- Daily trend with average and peak values.
SELECT TRUNC(CAST(sample_time AS DATE)) AS sample_day,
       ROUND(AVG(cpu_util_pct), 2) AS avg_cpu_pct,
       ROUND(MAX(cpu_util_pct), 2) AS max_cpu_pct,
       ROUND(AVG(avg_active_sessions), 2) AS avg_active_sessions,
       ROUND(MAX(avg_active_sessions), 2) AS max_active_sessions,
       ROUND(AVG(executions_per_sec), 2) AS avg_execs_per_sec,
       ROUND(MAX(segment_used_gb), 2) AS segment_used_gb
FROM   capacity_usage_snapshot
GROUP  BY TRUNC(CAST(sample_time AS DATE))
ORDER  BY sample_day;
-- p95 CPU and workload metrics from local snapshots.
SELECT ROUND(PERCENTILE_CONT(0.95) WITHIN GROUP (ORDER BY cpu_util_pct), 2) AS p95_cpu_pct,
       ROUND(PERCENTILE_CONT(0.95) WITHIN GROUP (ORDER BY avg_active_sessions), 2) AS p95_aas,
       ROUND(PERCENTILE_CONT(0.95) WITHIN GROUP (ORDER BY executions_per_sec), 2) AS p95_execs_per_sec,
       ROUND(MAX(segment_used_gb), 2) AS latest_segment_used_gb
FROM   capacity_usage_snapshot;

The following sizing example uses simple inputs. Replace the values with your measured p95 CPU, expected workload growth, target CPU headroom, current storage, and observed monthly growth. 

-- Simple sizing calculation for CPU and storage.
WITH input AS (
  SELECT 8     AS current_ecpus,
         65    AS p95_cpu_pct,
         70    AS target_cpu_pct,
         1.30  AS workload_growth_factor,
         1.8   AS storage_used_tb,
         0.18  AS monthly_growth_tb,
         12    AS planning_months,
         1.20  AS storage_headroom_factor
  FROM   dual
)
SELECT CEIL(current_ecpus * (p95_cpu_pct / target_cpu_pct) * workload_growth_factor)
         AS recommended_base_ecpus,
       CEIL((storage_used_tb + monthly_growth_tb * planning_months) * storage_headroom_factor)
         AS recommended_storage_tb
FROM   input;

Use Monitoring alarms for operational thresholds and Operations Insights for planning forecasts. The following examples are starting points; tune thresholds to the workload and service-level objectives.

Capacity signal Example alarm or forecast input Planning action
Sustained CPU pressure CpuUtilization[5m].mean() > 80 for a sustained window. Check top SQL and waits first, then evaluate base ECPU increase or compute auto scaling behavior.
Queued SQL QueuedStatements[5m].sum() > 0 during user-facing windows. Review service selection, concurrency, parallelism, locks, and CPU headroom.
Storage pressure StorageUtilization[1h].mean() > 80 or forecasted high utilization in Operations Insights. Estimate growth, enable or adjust storage auto scaling, compress large tables, or remove unused data.
I/O growth Rising IOPS, IOThroughput, or physical read/write byte metrics. Review top SQL, partitioning, compression, indexing, and batch windows before increasing capacity.
Fleet growth Operations Insights top consumers and growth-rate views. Prioritize databases with high utilization and high growth over databases with isolated spikes.

Expected results

  • The growth query should show the observed storage delta and an estimated monthly growth rate.
  • The daily trend should show whether CPU, active sessions, execution rate, and storage are rising, stable, or tied to specific windows.
  • The p95 query should provide a better planning signal than a single maximum spike.
  • In the sizing example, 8 current ECPUs at 65% p95 CPU, with 30% workload growth and a 70% target CPU level, produces a recommendation of 10 base ECPUs.
  • In the same example, 1.8 TB current storage plus 0.18 TB monthly growth for 12 months with 20% headroom produces a recommendation of 5 TB.
  • If queued statements or active sessions rise while CPU stays low, investigate waits, service selection, locks, or SQL shape before scaling CPU.
  • OCI Monitoring should show whether the database is approaching CPU, storage, session, or I/O thresholds at the service level.
  • Operations Insights should identify top consumers, growth trends, and forecasted CPU or storage pressure for individual databases or fleets.
  • Auto scaling decisions should be based on observed utilization, forecast horizon, workload criticality, and billing impact.
