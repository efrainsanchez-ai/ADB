Automatic Performance Tuning

Automatic performance tuning combines optimizer statistics, SQL Plan Management, resource management, and monitoring. The goal is not to remove all tuning work. The goal is to keep routine optimization current and give teams reliable evidence when a workload changes.

What it is

Automatic performance tuning in Autonomous Database is a set of managed capabilities rather than one feature switch. The database collects optimizer statistics, supports SQL Plan Management to reduce plan regression risk, applies service-based resource management, and exposes workload diagnostics through Database Actions, Performance Hub, SQL Monitor, AWR, and ASH where available.

Performance Tuning Loop
Observe Top SQL, waits, AAS, CPU, I/O, and service usage.
Maintain Optimizer statistics, histograms, and stale object checks.
Stabilize SQL Plan Management and accepted execution plans.
Prioritize Connection services and resource consumer groups.
Validate Actual plans, row counts, and measurable SQL results.

Color guide: blue-accent cards highlight performance metrics or telemetry, gray-accent cards highlight validation points, and plain cards show normal tuning process steps.

Area What to review Why it matters
Optimizer statistics Object statistics, stale statistics, histograms, and row-count estimates. Bad cardinality estimates are a common cause of poor join order, access path, and parallelism choices.
SQL Plan Management Automatic plan evolution mode and accepted SQL plan baselines. Stable plan selection helps reduce regressions after workload, data, or version changes.
Resource management Service name, consumer group, queued statements, and active sessions. Different workloads need different concurrency and priority behavior.
Monitoring Top SQL, waits, average active sessions, CPU, I/O, and SQL execution plans. Performance work should start from measured bottlenecks, not assumptions.

Why it matters

Most tuning investigations start with the same questions: did the optimizer estimate correctly, did the SQL plan change, is the system CPU-bound or wait-bound, and is the application connected to the right service? Autonomous Database automates routine maintenance, but teams still need practical checks to confirm the current state and decide whether to tune SQL, gather statistics, adjust connection services, or scale resources.

Check if enabled

Start with optimizer statistics and SQL Plan Management. These queries are intentionally read-only. Use DBA_ views when you have the privileges; otherwise use matching USER_ views where possible. 

SET LINESIZE 220
SET PAGESIZE 100
SET TRIMSPOOL ON
SET TAB OFF
COLUMN client_name FORMAT A38
COLUMN status FORMAT A18

SELECT client_name, status
FROM   dba_autotask_client
WHERE  client_name = 'auto optimizer stats collection';
SET LINESIZE 220
SET PAGESIZE 100
SET TRIMSPOOL ON
SET TAB OFF
COLUMN table_name FORMAT A32
COLUMN object_type FORMAT A16
COLUMN last_analyzed FORMAT A22
COLUMN stale_stats FORMAT A12

SELECT table_name,
       num_rows,
       blocks,
       last_analyzed,
       stale_stats
FROM   user_tab_statistics
WHERE  object_type = 'TABLE'
AND    (last_analyzed IS NULL OR stale_stats = 'YES')
ORDER  BY last_analyzed NULLS FIRST;
SET LINESIZE 220
SET PAGESIZE 100
SET TRIMSPOOL ON
SET TAB OFF
COLUMN parameter_name FORMAT A40
COLUMN parameter_value FORMAT A30

SELECT parameter_name, parameter_value
FROM   dba_sql_management_config
WHERE  parameter_name = 'AUTO_SPM_EVOLVE_TASK';

For SQL plan review, inspect the baseline attributes before approving, fixing, disabling, or dropping any plan. The key columns are ACCEPTED, ENABLED, FIXED, REPRODUCED, and AUTOPURGE. 

SET LINESIZE 220
SET PAGESIZE 100
SET TRIMSPOOL ON
SET TAB OFF
COLUMN sql_handle FORMAT A32
COLUMN plan_name FORMAT A32
COLUMN enabled FORMAT A8
COLUMN accepted FORMAT A8
COLUMN fixed FORMAT A8
COLUMN reproduced FORMAT A10
COLUMN autopurge FORMAT A10
COLUMN origin FORMAT A22

SELECT sql_handle,
       plan_name,
       enabled,
       accepted,
       fixed,
       reproduced,
       autopurge,
       origin,
       last_verified,
       last_executed
FROM   dba_sql_plan_baselines
ORDER  BY last_modified DESC
FETCH FIRST 30 ROWS ONLY;

SET PAGESIZE 100
SET TRIMSPOOL ON
SET TAB OFF

SET LONGCHUNKSIZE 100000

COLUMN plan_name FORMAT A32

SELECT *

         plan_name  => '<plan_name>',

       ));

Then check current workload pressure. High average active sessions with high CPU points to CPU saturation. High active sessions with a dominant wait class points to a wait bottleneck. 

SET LINESIZE 220
SET PAGESIZE 100
SET TRIMSPOOL ON
SET TAB OFF
COLUMN metric_name FORMAT A42
COLUMN metric_unit FORMAT A28

SELECT metric_name, value, metric_unit
FROM   v$sysmetric
WHERE  metric_name IN (
  'Host CPU Utilization (%)',
  'Average Active Sessions',
  'Executions Per Sec',
  'User Calls Per Sec'
)
ORDER BY metric_name;
SET LINESIZE 220
SET PAGESIZE 100
SET TRIMSPOOL ON
SET TAB OFF
COLUMN service_name FORMAT A30
COLUMN consumer_group FORMAT A30

SELECT service_name,
       resource_consumer_group,
       COUNT(*) AS sessions
FROM   v$session
WHERE  username IS NOT NULL
GROUP  BY service_name, resource_consumer_group
ORDER  BY sessions DESC;

How to enable

Automatic statistics gathering is enabled for Autonomous Database. For tables that have just received large conventional DML changes, gather stale statistics explicitly. For SQL Plan Management, choose the automatic SPM mode that matches the review model for the workload. 

SET LINESIZE 220
SET PAGESIZE 100
SET TRIMSPOOL ON
SET TAB OFF
SET SERVEROUTPUT ON

BEGIN
  DBMS_STATS.GATHER_SCHEMA_STATS(
    ownname          => USER,
    estimate_percent => DBMS_STATS.AUTO_SAMPLE_SIZE,
    method_opt       => 'FOR ALL COLUMNS SIZE AUTO',
    cascade          => TRUE,
    options          => 'GATHER STALE'
  );
END;
/

SET TRIMSPOOL ON
SET TAB OFF

EXEC DBMS_SPM.CONFIGURE('AUTO_SPM_EVOLVE_TASK', 'AUTO');

SET TAB OFF

EXEC DBMS_SPM.CONFIGURE('AUTO_SPM_EVOLVE_TASK', 'ON');

EXEC DBMS_SPM.CONFIGURE('AUTO_SPM_EVOLVE_TASK', 'OFF');

SQL Plan review and approval options

A DBA has several review paths for SQL Plan Management. Use automatic modes for routine protection, and use manual review when a specific SQL statement has business impact or when you need a documented approval step.

Option Setting or action When to use it
Real-time automatic SPM AUTO_SPM_EVOLVE_TASK = AUTO Validate plan changes during foreground execution and reduce regression risk for active SQL.
Background-verified automatic SPM AUTO_SPM_EVOLVE_TASK = ON Let the high-frequency SPM evolve task test and accept better plans in the background.
Disabled automatic SPM AUTO_SPM_EVOLVE_TASK = OFF Stop automatic SPM evolution when you need a controlled manual-only review window.
Report-only evolution verify => 'YES', commit => 'NO' Generate a plan evolution report without changing the accepted status.
Evolve Advisor review mode ACCEPT_PLANS = false Let the automatic task verify candidates and produce a report that a DBA can review before manual acceptance.
Manual verify and approve verify => 'YES', commit => 'YES' Accept a candidate only after Oracle verifies that it performs better than the current baseline plan.
Load known-good plan DBMS_SPM.LOAD_PLANS_FROM_CURSOR_CACHE Seed a baseline from a plan already observed in the cursor cache.
Fix a plan FIXED = YES Prefer one accepted plan for a targeted regression case. Use this sparingly.
Disable a plan ENABLED = NO Keep the baseline record but prevent the optimizer from using that plan.
Control purge behavior AUTOPURGE = YES or NO Allow stale baselines to age out, or retain a critical baseline for controlled workloads.

For the automatic SPM Evolve Advisor task, DBAs with the required privileges can control whether recommended plans are accepted automatically. Set ACCEPT_PLANS to false for report-first review, then inspect the automatic evolve report before taking manual action. 

SET LINESIZE 220
SET PAGESIZE 100
SET TRIMSPOOL ON
SET TAB OFF
SET SERVEROUTPUT ON

BEGIN
  DBMS_SPM.SET_EVOLVE_TASK_PARAMETER(
    task_name => 'SYS_AUTO_SPM_EVOLVE_TASK',
    parameter => 'ACCEPT_PLANS',
    value     => 'false'
  );
END;
/

SET TRIMSPOOL ON
SET TAB OFF

COLUMN parameter_value FORMAT A30

SELECT parameter_name, parameter_value
FROM   dba_advisor_parameters
WHERE  task_name = 'SYS_AUTO_SPM_EVOLVE_TASK'
AND    parameter_name = 'ACCEPT_PLANS';

When the known-good plan is already in the cursor cache, load it into a SQL plan baseline. Keep it non-fixed unless you have a clear regression-control reason to make it fixed. 

SET LINESIZE 220
SET PAGESIZE 100
SET TRIMSPOOL ON
SET TAB OFF
SET SERVEROUTPUT ON

DECLARE
  l_loaded PLS_INTEGER;
BEGIN
  l_loaded := DBMS_SPM.LOAD_PLANS_FROM_CURSOR_CACHE(
                sql_id          => '<sql_id>',
                plan_hash_value => <plan_hash_value>,
                fixed           => 'NO',
                enabled         => 'YES'
              );

  DBMS_OUTPUT.PUT_LINE('Plans loaded: ' || l_loaded);
END;
/

Test example

Use actual execution plans when validating SQL. EXPLAIN PLAN shows an estimated plan; DBMS_XPLAN.DISPLAY_CURSOR shows the plan that actually ran. 

SET LINESIZE 220
SET PAGESIZE 100
SET TRIMSPOOL ON
SET TAB OFF

CREATE TABLE perf_orders AS
SELECT level AS order_id,
       MOD(level, 1000) AS customer_id,
       DATE '2025-01-01' + MOD(level, 365) AS order_date,
       ROUND(DBMS_RANDOM.VALUE(10, 500), 2) AS order_amount
FROM   dual
CONNECT BY level <= 100000;
SET LINESIZE 220
SET PAGESIZE 100
SET TRIMSPOOL ON
SET TAB OFF
SET SERVEROUTPUT ON

BEGIN
  DBMS_STATS.GATHER_TABLE_STATS(
    ownname          => USER,
    tabname          => 'PERF_ORDERS',
    estimate_percent => DBMS_STATS.AUTO_SAMPLE_SIZE,
    method_opt       => 'FOR ALL COLUMNS SIZE AUTO',
    cascade          => TRUE
  );
END;
/
SET LINESIZE 220
SET PAGESIZE 100
SET TRIMSPOOL ON
SET TAB OFF

SELECT /*+ gather_plan_statistics */
       COUNT(*) AS order_count
FROM   perf_orders
WHERE  customer_id = 42;

SET PAGESIZE 100
SET TRIMSPOOL ON
SET TAB OFF
SET LONG 100000
SET LONGCHUNKSIZE 100000
COLUMN sql_id FORMAT A15

SELECT *
FROM   TABLE(DBMS_XPLAN.DISPLAY_CURSOR(
         sql_id => NULL,
         cursor_child_no => NULL,
         format => 'TYPICAL +IOSTATS LAST +PEEKED_BINDS'

To find SQL that deserves attention, start with elapsed time, CPU time, buffer gets, and disk reads. 

SET LINESIZE 220
SET PAGESIZE 100
SET TRIMSPOOL ON
SET TAB OFF
COLUMN sql_id FORMAT A15
COLUMN sql_text FORMAT A80

SELECT sql_id,
       executions,
       ROUND(elapsed_time / 1e6, 1) AS total_elapsed_sec,
       ROUND(elapsed_time / NULLIF(executions, 0) / 1e6, 3) AS avg_elapsed_sec,
       ROUND(cpu_time / 1e6, 1) AS total_cpu_sec,
       buffer_gets,
       disk_reads,
       parsing_schema_name,
       SUBSTR(sql_text, 1, 100) AS sql_preview
FROM   v$sqlarea
WHERE  executions > 0
ORDER  BY elapsed_time DESC
FETCH FIRST 20 ROWS ONLY;

Expected results

  • Automatic optimizer statistics collection should be enabled in normal Autonomous Database operation.
  • Real-time SQL Plan Management should show AUTO; background-verified automatic SPM should show ON; disabled automatic SPM should show OFF.
  • DBA_SQL_PLAN_BASELINES should clearly separate accepted, unaccepted, enabled, disabled, fixed, reproduced, and autopurge-enabled plans.
  • Report-only evolution should return an evolution report without changing ACCEPTED from NO to YES.
  • When ACCEPT_PLANS is false, the automatic evolve task should verify candidates and produce a report without accepting them automatically.
  • Manual approval with commit => 'YES' should accept only the qualifying plan after verification.
  • Fixed plans should be rare and tied to a specific regression-control requirement; disabled plans should remain visible but unavailable to the optimizer.
  • Execution plan output should include actual row statistics when the statement uses gather_plan_statistics.
  • Large gaps between estimated rows and actual rows usually point to statistics, histogram, bind selectivity, or predicate-shape issues.
  • Top SQL review should identify whether the immediate tuning target is CPU, logical I/O, physical I/O, waits, or concurrency.
