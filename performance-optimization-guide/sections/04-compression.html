Compression

Compression reduces storage and can reduce scan I/O. The right compression choice depends on workload type, load pattern, query pattern, and DML frequency.

What it is

Compression stores table data in fewer bytes. In Autonomous Database, defaults vary by workload. Lakehouse workloads use Hybrid Columnar Compression by default for tables. Transaction Processing, JSON, and APEX workloads default to no table compression. You can still specify compression explicitly for tables when the workload benefits from it.

Compression Tradeoff Map
Data Shape Repeated values and scan-heavy tables compress well.
Choice Column-store, row-store, or no compression.
Benefit Lower segment size and fewer blocks read during scans.
Test Validate DML cost, query I/O, and index status.

reduced
Scan I/O

Color guide: blue-accent cards highlight storage or I/O signals, gray-accent cards highlight test and validation points, and plain cards show normal compression choices.

Compression choice Typical fit Tradeoff to test
COLUMN STORE COMPRESS FOR QUERY HIGH Bulk-loaded, scan-heavy analytic tables. Best fit for direct-path loads and query scans; test frequent updates and merges carefully.
ROW STORE COMPRESS ADVANCED Mixed workloads where row-level DML still matters. Can reduce storage while being more suitable for DML than column-store compression.
NOCOMPRESS Staging, high-DML, or short-lived tables. Uses more storage but can avoid compression overhead for write-heavy patterns.

Why it matters

Compression can reduce physical I/O because fewer blocks need to be read for scan-heavy queries. It can also reduce allocated storage. For write-heavy tables, the best answer is not always maximum compression. Measure query improvement, DML cost, and segment size together.

Check if enabled

Check table compression attributes and current segment size before changing anything. Use segment size as a practical baseline. 

SET LINESIZE 220
SET PAGESIZE 100
SET TRIMSPOOL ON
SET TAB OFF
COLUMN table_name FORMAT A32
COLUMN compression FORMAT A12
COLUMN compress_for FORMAT A30

SELECT table_name,
       compression,
       compress_for
FROM   user_tables
WHERE  table_name IN ('SALES', 'SALES_COMP_TEST')
ORDER  BY table_name;
SET LINESIZE 220
SET PAGESIZE 100
SET TRIMSPOOL ON
SET TAB OFF
COLUMN segment_name FORMAT A36
COLUMN segment_type FORMAT A18

SELECT segment_name,
       segment_type,
       ROUND(bytes / POWER(1024, 2), 2) AS size_mb
FROM   user_segments
WHERE  segment_name IN ('SALES', 'SALES_COMP_TEST')
ORDER  BY segment_name, segment_type;

For larger schemas, rank tables by segment size and current compression status. 

SET LINESIZE 220
SET PAGESIZE 100
SET TRIMSPOOL ON
SET TAB OFF
COLUMN table_name FORMAT A32
COLUMN last_analyzed FORMAT A22
COLUMN segment_name FORMAT A36
COLUMN segment_type FORMAT A18
COLUMN compression FORMAT A12
COLUMN compress_for FORMAT A30

SELECT s.segment_name AS table_name,
       ROUND(s.bytes / POWER(1024, 3), 2) AS size_gb,
       t.compression,
       t.compress_for,
       t.num_rows,
       t.last_analyzed
FROM   user_segments s
JOIN   user_tables t
       ON t.table_name = s.segment_name
WHERE  s.segment_type = 'TABLE'
ORDER  BY s.bytes DESC
FETCH FIRST 20 ROWS ONLY;

How to enable

Use compression that matches the workload. For analytic tables loaded in bulk, column-store query compression is commonly appropriate. For transactional or frequently updated tables, test row-store compression or no compression. 

SET LINESIZE 220
SET PAGESIZE 100
SET TRIMSPOOL ON
SET TAB OFF

ALTER TABLE sales MOVE COLUMN STORE COMPRESS FOR QUERY HIGH;
SET LINESIZE 220
SET PAGESIZE 100
SET TRIMSPOOL ON
SET TAB OFF

ALTER TABLE sales MOVE ROW STORE COMPRESS ADVANCED;
SET LINESIZE 220
SET PAGESIZE 100
SET TRIMSPOOL ON
SET TAB OFF

ALTER TABLE sales MOVE NOCOMPRESS;
A table move changes the physical segment. Validate index status and application maintenance requirements after a move. Test this operation in a non-production environment before using it on important application tables.

Test example

This example creates compressible data, records the segment size, compresses the table, and compares the resulting size and query plan statistics.

SET TAB OFF

SELECT level AS sale_id,
       MOD(level, 100) AS product_id,
       MOD(level, 5000) AS customer_id,
       DATE '2025-01-01' + MOD(level, 365) AS sale_date,
       RPAD('repeatable text value', 200, 'x') AS description
FROM   dual
CONNECT BY level <= 500000;

Validate query behavior by comparing logical and physical I/O before and after compression. 

SET LINESIZE 220
SET PAGESIZE 100
SET TRIMSPOOL ON
SET TAB OFF

SELECT /*+ gather_plan_statistics */
       product_id,
       COUNT(*) AS sales_count,
       SUM(sale_id) AS sale_id_sum
FROM   sales_comp_test
WHERE  sale_date >= DATE '2025-06-01'
AND    sale_date <  DATE '2025-07-01'
GROUP  BY product_id;
SET LINESIZE 220
SET PAGESIZE 100
SET TRIMSPOOL ON
SET TAB OFF
SET LONG 100000
SET LONGCHUNKSIZE 100000
COLUMN sql_id FORMAT A15

SELECT *
FROM   TABLE(DBMS_XPLAN.DISPLAY_CURSOR(
         sql_id => NULL,
         cursor_child_no => NULL,
         format => 'TYPICAL +IOSTATS LAST'
       ));

Expected results

  • USER_TABLES.COMPRESSION should show ENABLED after compression.
  • USER_TABLES.COMPRESS_FOR should show the selected compression method.
  • Segment size should decrease when the data pattern is compressible.
  • Scan-heavy queries may show fewer physical reads or lower storage scan volume.
  • Frequent UPDATE and MERGE workloads should be tested before using column-store compression.
